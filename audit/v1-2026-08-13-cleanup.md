## 11 — Schedule row deletion corrupts a focused input

**File:** `src/components/site-builder/SiteBuilder.tsx:243`

### Failure scenario

A couple has 4 schedule rows. They are actively typing in the 'detail' field of row 3 when they click delete on row 1. The array is rebuilt via `.filter((_, i) => i !== 0)`, so what was row 3 is now row 2. React reconciles by index — the DOM node (and the user's cursor) that was row 3's input is reused for the new row 2's data. The field the user is mid-edit now shows row 2's content; their keystrokes from this point overwrite a different schedule entry.

**Fix:** key schedule rows by a stable id, not array index.

## 12 — Hydration guard applied to counters but not the task list

**File:** `src/components/tools/Checklist.tsx:64`

**Also affects:** `Timeline.tsx`, `Settings.tsx`

### Failure scenario

A returning user who has completed 18 tasks, added 3 custom tasks, and removed 2 seed tasks opens `/dashboard/tasks`. The component renders immediately from store defaults: all 44 seed tasks unchecked, no custom tasks, no removed tasks — then one re-render later, after hydration, the real state replaces the seed list with a visible flash.

The same pattern occurs in `Timeline.tsx` (task bands rendered ungated) and `Settings.tsx` (form fields show defaults until hydration).

## 13 — `daysUntil()` off by one in non-UK timezones

**File:** `src/lib/utils.ts:39`

### Failure scenario

Couple sets wedding date to 1 June 2026. `new Date('2026-06-01')` is midnight UTC. In the UK during BST (UTC+1) this reads back correctly. But a couple accessing from New York (UTC-5) computes `startOfDay` via `getFullYear()/getMonth()/getDate()`, which reads the UTC-midnight instant as 31 May 2026 locally. `daysUntil()` returns one too many days; the dashboard countdown and timeline band thresholds are wrong. The effect persists until midnight local time on the actual wedding date.

## 15 — Search query desyncs from URL on back/forward navigation

**File:** `src/components/gallery/InspirationGallery.tsx:44`

### Failure scenario

User on `/inspiration` types 'garden', results update. They follow a `<Link href='/inspiration?q=coastal'>` navigation. `params.get('q')` is now 'coastal' and results immediately show coastal items (results derives from params directly), but the visible search input still shows 'garden' — because `query` state was seeded from URL only at mount and the debounce effect writes only `query→URL`, never `URL→query`.

All other filters correctly derive from params via `useMemo` on every render; search query alone is out of sync. Browser back/forward produces the same mismatch.
